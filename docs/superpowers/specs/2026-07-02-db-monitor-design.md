# 数据库监控页面设计

## 1. 背景

当前项目已经有 `缓存监控`、`在线用户`、`服务器监控` 页面，前端接入方式集中在 `admin-ui/apps/backend/src/views/system/monitor/*`，接口集中在 `admin-ui/apps/backend/src/api/system/monitor.ts`。现阶段需要补一个“数据库监控”页面，保持和现有监控体系一致，但范围只覆盖第一版可落地能力。

本设计以 PostgreSQL 为唯一目标数据库类型，面向后台管理员，用于查看数据库分组的连接状态、事务概况和实时趋势，不扩展为数据库运维中心。

## 2. 目标与非目标

### 2.1 目标

第一版数据库监控页面需要满足以下目标：

1. 支持按数据库分组切换监控视角。
2. 展示当前分组的基础概览信息，包括连接状态、连接池相关统计、数据库大小、事务与缓存命中率等。
3. 展示最近一段时间的实时趋势，包括事务吞吐、回滚/错误趋势，以及在能力可用时展示平均执行耗时和慢查询次数。
4. 明确展示当前分组的监控能力状态，尤其是 `pg_stat_statements` 是否可用。
5. 兼容能力降级与连接异常场景，页面不能因为部分指标不可用而整体失效。

### 2.2 非目标

第一版明确不做以下内容：

1. 不支持 MySQL、SQLite、SQL Server 等非 PostgreSQL 数据库。
2. 不做会话列表、终止会话、锁等待明细等运维操作。
3. 不做慢 SQL 明细、SQL 文本下钻、Top SQL 排行。
4. 不做跨天历史趋势存储。
5. 不做告警规则配置、告警推送。
6. 不引入 Prometheus、Grafana 或额外时序存储。

## 3. 范围约束与关键假设

### 3.1 范围约束

1. 页面类型为“概览 + 实时指标”。
2. 监控数据来源为 PostgreSQL 原生系统视图，不做应用埋点统计。
3. 页面刷新方式采用前端轮询，不引入 WebSocket。
4. 趋势数据只保存在当前服务实例内存中，不新增数据库表。

### 3.2 关键假设

1. 项目当前以 PostgreSQL 为主数据库，且数据维护逻辑已经直接依赖 PostgreSQL 视图，这与本设计一致。
2. 数据库分组由 GoFrame `g.DB(groupName)` 提供，页面只监控配置中存在的分组。
3. 部分增强指标依赖 `pg_stat_statements` 扩展；如果扩展不可用，页面允许降级展示。

## 4. 方案选择

本功能采用“PostgreSQL 原生视图 + 可降级增强 + 进程内短周期采样”的方案。

选择理由如下：

1. 与“数据库原生采集”的需求一致，不引入额外监控体系。
2. 能在第一版内同时满足“当前快照”和“最近趋势”两个目标。
3. 改动集中在已有监控模块附近，复用现有前后端组织方式。

不采用纯快照页的原因是无法稳定提供趋势图；不采用持久化采集方案的原因是会显著扩大第一版范围。

## 5. 页面设计

### 5.1 总体结构

页面采用 `顶部固定摘要 + 下方标签分区` 的 `C+` 布局，兼顾扩展性与首屏状态感。

结构如下：

1. 顶部工具栏
   - 数据库分组选择
   - 自动刷新开关
   - 刷新间隔，固定提供 `10s / 30s / 60s` 三档，默认 `10s`
   - 手动刷新按钮
   - 最近刷新时间
2. 顶部摘要条
   - 固定展示关键指标，不随标签切换
3. 下方标签区
   - `概览`
   - `实时指标`
   - `能力状态`

### 5.2 顶部摘要条

顶部摘要条固定展示以下 6 个关键指标：

1. 连接状态
2. 当前连接数
3. 活跃连接数
4. 数据库大小
5. 缓存命中率
6. 慢查询能力状态

设计原则：

1. 用户进入页面后无需切换标签即可判断数据库是否总体健康。
2. 即使增强指标不可用，也可以保留基础健康感知。

### 5.3 标签设计

#### 概览

用于展示当前分组的静态或准实时基础信息，固定包含：

1. PostgreSQL 版本
2. 数据库名
3. 最大连接数
4. 当前连接数
5. 活跃连接数
6. 空闲连接数
7. 等待连接数
8. 事务提交数
9. 事务回滚数
10. 缓存命中率
11. 数据库大小

#### 实时指标

用于展示最近一段时间的趋势图，第一版控制在 3 个图表以内：

1. `TPS / 事务吞吐`
2. `回滚 / 错误趋势`
3. `平均执行耗时 / 慢查询次数`

其中：

1. `TPS / 事务吞吐` 和 `回滚趋势` 使用 PostgreSQL 原生统计视图差值计算。
2. `平均执行耗时 / 慢查询次数` 仅在 `pg_stat_statements` 可用时展示。

#### 能力状态

用于解释当前分组能展示哪些指标，固定包含：

1. `pg_stat_statements` 是否启用
2. 当前用户是否有权限访问相关视图
3. 哪些增强指标可用
4. 哪些增强指标因扩展缺失或权限不足而被降级

### 5.4 交互规则

1. 切换数据库分组时，整页重新拉取该分组快照与趋势数据。
2. 自动刷新只作用于当前选中的分组。
3. 自动刷新不在后台预热其他分组。
4. 手动刷新立即刷新当前分组全部数据。
5. 页面初次进入默认加载 `default` 分组；若不存在，则加载后端返回的首个可用分组。

## 6. 后端设计

### 6.1 接口设计

第一版新增两组接口：

1. `GET /system/dbMonitor/groups`
   - 返回可监控的数据库分组列表
   - 字段至少包含：
     - `groupName`
     - `isDefault`
     - `dbType`
2. `GET /system/dbMonitor/monitor?groupName=default`
   - 返回某个分组的完整监控数据

`/system/dbMonitor/monitor` 的响应固定分为以下部分：

1. `overview`
   - 当前快照信息
2. `summary`
   - 顶部摘要条需要的关键指标
3. `timeseries`
   - 趋势序列
4. `capabilities`
   - 能力与降级信息
5. `alerts`
   - 页面内提示信息，不是告警系统

### 6.2 数据来源

第一版数据来源限定为 PostgreSQL 原生系统视图和函数：

1. `pg_stat_database`
   - 获取数据库级事务、回滚、缓存命中相关数据
2. `pg_stat_activity`
   - 获取当前连接、活跃连接、空闲连接、等待连接等数据
3. `pg_database_size`
   - 获取数据库大小
4. `pg_settings`
   - 获取 `max_connections` 等配置
5. `pg_stat_statements`
   - 在可用时获取平均执行耗时、查询次数与慢查询相关增强指标

### 6.3 采样模型

后端采样分为两层：

1. 请求时快照
   - 每次接口请求直接查询当前分组的最新数据库状态
2. 进程内采样器
   - 后台按固定周期对每个访问过的分组采样
   - 将最近一段时间的点位保存在内存环形缓冲区

采样器规则：

1. 按 `groupName` 隔离缓存。
2. 每个分组固定保留最近 60 个点位。
3. 服务重启后趋势数据允许清空，从头重新采样。
4. 首次进入页面时如果历史点位不足，允许前端显示“数据采集中”。

### 6.4 能力降级

以下场景需要显式降级：

1. `pg_stat_statements` 扩展未启用
   - `平均执行耗时`、`慢查询次数` 返回空值
   - `capabilities` 明确提示原因
2. 当前数据库账户无权读取相关视图
   - 返回可识别的能力缺失信息
3. 数据库分组不存在
   - 返回明确错误，而不是空结果
4. 数据库连接异常
   - 保留错误态响应，由前端展示异常状态

## 7. 前端设计

### 7.1 文件组织

按现有监控模块结构接入，新增文件如下：

1. `admin-ui/apps/backend/src/views/system/monitor/db/index.vue`
2. `admin-ui/apps/backend/src/api/system/monitor.ts` 中的数据库监控类型与接口

前端第一版默认采用单页面文件实现，不新增通用监控框架层；只有在图表配置重复明显时，才允许新增一个页面内聚的本地辅助文件。

### 7.2 展示原则

1. 页面整体风格对齐现有 `server` 与 `cache` 监控页。
2. 概览与能力说明优先可读性，不追求过度复杂交互。
3. 趋势图数量保持克制，避免第一版页面信息噪音过大。
4. 当增强指标缺失时，显示明确空态与原因，不显示伪造零值。

### 7.3 错误与空态

前端必须区分以下状态：

1. 正常态
   - 概览与趋势完整显示
2. 降级态
   - 基础概览正常，增强图表显示能力缺失提示
3. 异常态
   - 分组错误或接口失败时，摘要条与标签内容显示错误提示
4. 采样预热态
   - 趋势点位不足时显示“数据采集中”

## 8. 权限与菜单

第一版数据库监控页接入现有菜单与权限体系：

1. 新增菜单路由，路径固定为 `system/monitor/db/index`
2. 新增页面权限标识，固定命名为：
   - `system:dbMonitor`
   - `system:dbMonitor:groups`
   - `system:dbMonitor:monitor`

## 9. 测试与验证

### 9.1 后端

需要覆盖以下验证点：

1. 分组不存在时返回明确错误。
2. PostgreSQL 快照数据能正确映射到统一响应结构。
3. `pg_stat_statements` 不可用时返回正确的能力降级信息。
4. 采样器按分组隔离，且点位数量受上限控制。
5. 首次采样不足时，趋势数据返回符合前端预期的空序列或短序列。

### 9.2 前端

需要覆盖以下验证点：

1. 正常态下摘要条、概览标签、实时指标标签都能正确显示。
2. 降级态下增强图表显示空态提示，能力标签显示原因。
3. 异常态下页面有明确提示，而不是空白。
4. 切换分组后不会残留上一个分组的摘要或趋势数据。
5. 自动刷新只刷新当前分组。

### 9.3 联调

至少完成以下联调检查：

1. `default` 分组可正常展示监控数据。
2. 一个额外分组可正常切换与刷新。
3. 服务重启后趋势图允许重新积累，不视为缺陷。

## 10. 风险与后续扩展

### 10.1 已知风险

1. 趋势数据保存在单实例内存中，多实例部署下各实例趋势不共享。
2. `pg_stat_statements` 依赖数据库扩展和访问权限，部分环境无法展示增强指标。
3. PostgreSQL 原生统计视图存在统计刷新粒度限制，趋势图不是毫秒级实时。

### 10.2 后续扩展方向

不属于第一版，但后续可扩展为：

1. 持久化趋势数据
2. 慢 SQL 明细
3. 会话列表与终止会话
4. 多数据库类型支持
5. 告警规则与通知

## 11. 结论

第一版数据库监控页面采用 `PostgreSQL 原生视图 + 进程内短周期采样 + 顶部摘要 + 标签分区` 的方案，优先实现“能稳定展示分组数据库概览与实时趋势”，并通过显式能力状态处理 `pg_stat_statements` 不可用场景。该方案改动范围可控，贴合项目现有监控模块结构，适合作为第一版落地基线。
